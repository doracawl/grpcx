grpcx

从零自研的 Rust + TypeScript RPC 栈 · 同主机 / 同网段路径全自管

grpcx 不是 gRPC 的封装,也不是基于现有 IPC 框架的胶水层。底层从 OS reactor + 系统调用桥开始, 自研 10 个 crate 分层堆到 gRPC 兼容的 façade,加 6 个 TS package 走 N-API 在 Node 侧并行实现等价 client。 第一个落地工作流是 internal-RPC v1:对外提供 wire format v2 + 三种 transport, 每一种都按"对手开源 SOTA"的角度做了 8 轮 perf 攻关,绝大多数 RFC § 8 gate 达到或超越 user-space 物理 floor。

0. 我们是什么

把 grpcx 拆成三个面去看:

① 通信底座

从系统调用一层一层堆上来 — grpcx-io(io_uring / kqueue / epoll 原语)→ grpcx-rt(reactor + runtime)→ grpcx-{quic,h3,h2,ws,wt,crypto} 是六个独立的协议 crate。每个都可单独发布给非 RPC 项目用,纯粹的"石头"层。

② RPC 框架

grpcx 顶层 crate + grpcx-pb codegen。提供:1)RpcChannel trait,统一 client side 调用面;2)Service::dispatch_with_ctx trait,统一 server side 分派面;3)Server + listen_* 方法,统一 server lifecycle。

③ 跨语言互操作

TS 端 6 个 npm package + 1 个 N-API addon。@grpcx/native 桥接到 Rust transport 库,@grpcx/transport-* 各包提供 idiomatic TS API。Rust server ↔ TS client 端到端跨语言验证 KAT 通过(_dev/kat-vectors/9.*.hex + e2e tests)。

Figure 1 — 架构 stack(从 OS syscall 一层一层到 application)
9 层从底向上:OS syscall → grpcx-io → grpcx-rt(reactor)→ wire v2 codec → 3 transports → RpcChannel trait/Service dispatch → grpcx-pb codegen → Rust 或 TS application → 业务代码。 紫色框是独立可发布 sister crate(QUIC/HTTP/2/HTTP/3/WS/WT/crypto),不在本批次 v1 改动面,但共用 grpcx-rt + grpcx-io 底座。

1. 我们能做什么

★ transport-{uds,shmem,tcp-mux v2} 三种是 internal-RPC v1 的工作面。所有都跑同一个 wire v2。 通过 RpcChannel trait 同一个 codegen-stub 可以挂到任何 transport。

1.2 RPC 调用形态(全部 4 种 + 1 个 zero-copy 变体)

Unary

call_unary(svc, method, meta, body) → (resp, trailing)

同步语义,1 BEGIN + 1 END (可带 inline body)。所有 3 transport 通过。bench gate shmem-rtt-busy / uds-rtt / tcpmux-rtt 测的就是这个。

Server-streaming

call_server_streaming(svc, method, meta, body) → (Vec<resp>, trailing)

1 BEGIN + N DATA + 1 END(meta only)。bench shmem-throughput 用 server-streaming 推 N×3 KiB 帧。

Client-streaming

call_client_streaming(svc, method, meta, bodies[]) → (resp, trailing)

1 BEGIN(可带首帧)+ N-1 DATA + 1 END(server END 触发 dispatch)。

Bidi(half-duplex v1)

call_bidi(svc, method, meta, bodies[]) → (Vec<resp>, trailing)

v1 是 half-duplex(全发再全收);full-duplex 是 v1.x 议题。e2e 测试 bidi_three_each_way 三套 transport 全过。

★ Zero-copy server-streaming view(v1.5+,shmem 专属)

call_server_streaming_view<F: FnMut(&[u8])>(svc, method, meta, body, on_data) → trailing

每个 Data 帧的 payload 通过 borrowed slice &[u8] 投递到回调,不 memcpy 出 shmem 槽,不 V8 alloc。lx64 shmem-throughput 从 1.49 GB/s 推到 34.04 GB/s 主要靠这条 API。 Owned Vec<Vec<u8>> 版本保留给需要 owned data 的 caller。

Figure 2 — Unary RTT sequence(shmem busy-poll mode,2 frames per RPC)
单 unary RPC 2 帧(BEGIN client→server + END server→client),双 SPSC ring(c2s / s2c)。 Busy-poll-unbounded 模式跳过所有 wake-fd syscall,producer/consumer 都自旋于 ring head/tail。 Rust 实测 min 515 ns(纯用户态);TS+N-API+shmem 5.44 µs(加上 7+ N-API crossing + V8 alloc + libuv 调度 ≈ 4.9 µs floor)。

1.3 Wire 协议 v2(摘要,完整 SPEC 在 _dev/SPEC-wire-v2.md)

16-byte 固定 header

stream_id u32 | frame_type u8 | flags u8 | metadata_count u16 | payload_len u32 | reserved u32

常时间 zero-branch happy-path decode_header(cargo asm 验证)。Encode 走单次 copy_from_slice 写到 stack buffer。

Metadata block

变长 entries: name_len u16 | value_len u32 | name | value 重复 N 次。Decode 是 zero-copy(返 &[u8] view)。Encode 经 encode_metadata_block 单遍写。

Pseudo headers

4 个保留 name: :service / :method / :kind / :status。wire_v2::pseudo 子模块带预编码 STATUS_OK_BLOCK(17 bytes)和 encode_begin_block(stack-buffer 单遍写)。

Frame types

6 种:Begin(req 起手)· Data(stream chunk)· End(收尾 + 可带 trailing meta + 可带 inline body)· Reset(错误码 + 消息)· Ping / Pong(keepalive)。

Figure 3 — shmem region 内存布局(MIN_REGION_BYTES = 131 328 ≈ 128 KiB,v1.3 后)
每个 SPSC ring 一个方向。4 个 AtomicU64 pos 各占独立 cache line(64 B)避免 false sharing。 v1.3 把 SLOTS_PER_RING 从 4 → 16;v1.5 加 Rigtorp cached pos + zero-copy view;v1.9 Linux 切 eventfd。 region size 用 rendezvous UDS 协商,TS N-API mirror(ts/packages/grpcx-native/src/transport_shmem.h 的 kSlotsPerRing)必须同步。

1.4 场景与典型部署模式

能力清单(1.1–1.3)是"我们能做什么";下面 7 个场景是"实际怎么用" — 每个一个真实部署形态,标清楚几台设备 / 几个进程,走哪条 transport,关键能力是什么。

Scenario 1

同主机信任域内极致 latency / 高吞吐 IPC

两个进程在同一台机器,信任彼此,要把 RPC 推到用户态硬件 floor。

Transport
transport-shmem · 双端 set_busy_poll_unbounded(true) + listen_shmem_busy_poll_until
实测数字 (lx64)
RTT min 515 ns · 持续 34 GB/s server-streaming (zero-copy view)
限制
frame ≤ 4 KiB (v1) · 每连接 128 KiB region · 烧 1 CPU/连接 (busy-poll mode)
典型用例
数据库 ↔ 查询引擎、推理 server ↔ ML preprocessor、log/metric pipeline、bulk transfer 流水线
Scenario 2

同主机 daemon + N clients,内核 attest peer credentials

守护进程要鉴权 caller 是谁(uid/gid/pid),不能信任应用层 token。

Transport
transport-uds · CallContext::peer_cred() 暴露内核 attest 的 uid/gid/pid
关键能力
内核 SO_PEERCRED 不可伪造,handler 入口判一下就拒了未授权 caller。shmem / tcp-mux 无等价能力。
实测数字 (lx64)
RTT 5.56 µs · 已 at Linux 6.12 syscall floor(6 syscalls × 930 ns)
典型用例
systemd 风格 service / Docker daemon / dbus 替代 / Unix-y service mesh / 多租户 daemon ACL
Scenario 3

跨语言混合栈(Rust server + Node/TypeScript client)

服务用 Rust 写,client 来自不同语言 — N-API 桥到 Node,UDS 给其他语言 stdlib 直接接。

Transport
transport-uds(其他语言 stdlib)+ transport-shmem(via @grpcx/native N-API addon)
关键能力
Rust 一份 .proto + grpcx-pb 两 backend → Rust client stub + TS namespace。Server 一次 listen 多 transport,client 按需选。
实测验证
e2e cross-language 3 transport × 4 RPC shape = 12 用例 / KAT byte-level 双 codec 验证。lx64 TS shmem 5.44 µs / TS UDS 15.98 µs。
典型用例
多语言混合栈、Node tooling 接 Rust backend、Python ML preprocessor 喂 Rust 推理 server
Scenario 4

跨主机 gRPC 互操作(对接 tonic / grpc-go / grpc-java)

grpcx 服务要被 mainstream gRPC 客户端调用 — 或者反过来 grpcx 去调 tonic。

Transport
transport-h2 / transport-h2-tls · sister crate grpcx-h2 + grpcx-crypto
关键能力
wire 是 standard gRPC over HTTP/2,跟 tonic / grpc-go / grpc-java 字节级兼容。comparators/tonic-grpcx 做 e2e 对照 bench。
定位
不是 v1 internal-RPC 工作面 — 是 grpcx 跨主机互操作面,本会话未动 perf。
典型用例
对接遗留 gRPC 服务、被第三方 gRPC client 调用、跨语言 grpc 互通
Scenario 5

跨主机弱网链路(高 RTT / 高丢包 / 移动)

跨数据中心 / 移动客户端 / 不稳定网络,要 0-RTT 重连和 head-of-line blocking 免疫。

Transport
transport-h3 · 由 sister crates 组成:grpcx-h3(HTTP/3) + grpcx-quic(QUIC) + grpcx-crypto(TLS 1.3)
关键能力
0-RTT 重连(QUIC session tickets)· 跨 stream 独立 flow control(不像 HTTP/2 单 TCP head-of-line)· connection migration(IP 变了不断 RPC)
定位
sister crate 集成,本会话未动 perf;`comparators/tonic-grpcx` 对照 tonic h2 over TCP
典型用例
跨区域服务同步、移动 app ↔ 后端、edge ↔ origin、cellular 网络
Scenario 6

浏览器 / proxy 中转(需要单 TCP 多路复用)

浏览器只能开少量 connection · CDN 中转要 multiplex · 或者 proxy 链路不允许多 TCP。

Transport
transport-ws-mux(浏览器 / proxy 中转)· transport-tcp-mux v1(纯 TCP + mux 但无 WS shell · 共用 mux frame grammar)
关键能力
N 个 RPC stream 复用单根 connection · stream-id 区分 · 跟 grpcx 内部其他 transport 共享同一 codegen-stub
v1 vs v2 区分
mux-frame wire v1(mod mux + mod tcpmux)是 multiplex 设计;wire v2(本会话工作面)是 1-stream/connection 走 connection pool。两条 wire 并行存在不替换。
典型用例
Web app real-time、CDN edge 接 grpcx backend、Cloudflare Workers / Vercel edge,proxy-friendly
Scenario 7

混合部署 — 同一 service 既本机又远端

dev 环境 local IPC、prod 环境跨主机;同一份业务代码,只在 client 选 transport。

Transport
多个并存 — UDS local + tcp-mux v2 远端 + (可选)transport-h3 跨 DC。Box<dyn RpcChannel> 容器化
关键能力
同一份 .proto + codegen-stub 通过 RpcChannel trait 挂任何 transport。call site 不变,部署时换 connection。
实测
Cross-language e2e 已验证 4 RPC shape × 3 transport = 12 用例。同一 codegen-stub 跨 transport 字节级行为一致(KAT)。
典型用例
dev local + prod remote、blue/green migration、service mesh 同 host 短路、shared lib 既给本机也给远端用

2. 工作流程

2.1 开发者视角(写一个新 service 端到端)

STEP 1
写 .proto
标准 proto3,定义 service + 4 种 RPC 形态。可跨语言。
STEP 2
grpcx-pb codegen
Rust backend 生成 XxxClient + XxxServer<T> trait;TS backend 生成 namespace + 类型。1000-method codegen ~ 1.5 ms(RFC < 1 s)。
STEP 3
实现 server
impl Service::dispatch_with_ctx。CallContext 带 peer_cred()(UDS/shmem)和 trailing metadata 累积。
STEP 4
绑 transport + listen
server.listen_uds_until(...) / listen_shmem_until(...) / listen_tcp_mux_v2_until(...),opt-in 变体加 _busy_poll_。
STEP 5
client connect + call
UdsConnection::connect / ShmemConnection::connect / TcpMuxV2Connection::connect,然后 conn.call_unary(...)。同一个 codegen-stub 通过 RpcChannel trait 挂到任何 transport。

2.2 跨语言场景(Rust server + TS client)

STEP 1
同一份 .proto
Rust 端走 grpcx-pb Rust backend;TS 端走 grpcx-pb TS backend(codegen_ts)。
STEP 2
Rust server bind
同 2.1 STEP 3-4。
STEP 3
TS rendezvous
TS 通过 @grpcx/transport-* 包连接到 socket path。@grpcx/native N-API addon 把 wire 编解码委托给 C++,但 v1.6+ 起 hot path(metadata + header)纯 JS-side 跑(去 N-API crossings)。
STEP 4
TS client call
await conn.callUnary(svc, method, ctx, body)。返回 [bytes, trailing]。
STEP 5
e2e KAT
_dev/kat-vectors/9.{1,2,3,4}*.hex 跨 Rust + TS 双 codec 字节级 round-trip 验证。ts/test/e2e_cross_language.test.mjs 跑 Rust server × TS client 三 transport × 4 RPC shape = 12 用例。

2.3 Perf 攻关视角(完整 Phase A→B dance)

PHASE 0
Bench validate
每改一次 perf 跑 bench(n ≥ 99,最好 10k+)。真动针 ≥ 1.5× variance band。在 noise 内 = polish 路径无效。
PHASE A
Decomposition (read-only)
2 个 sub-agent 并行:一个 map 我方完整 hot path × file:line × atomic-op count(目标 18+ stage);一个抓参考实现(竞品 SOTA / Aeron / DPDK / nginx / lmdb-js etc.)。±20% budget 对账实测。
PHASE B
Attack (worktree-isolated)
Top-N attack 清单(file:line + concrete change + 估 µs + semantic class + blast radius)。串行实施全部,cumulative bench validate 一次,不每 attack 单独跑。
PHASE C
翻盘对账
Phase A 预测 vs Phase B 实测对照表。翻盘项 = polish 永远碰不到的位置 — 这是 decomposition 的核心价值。本项目 6 次应用,4 次有翻盘 / 2 次预测吻合。
PHASE D
Earned ceiling 或 Round 4
如果还差 → §3 Round 4+ 重新 decompose(不许 polish 同一 attack 清单)。如果真没 attack 可做 → 才合法 declare ceiling(每个剩余 gate 都给出 per-syscall 一致性证明)。
核心 rule(perf-decomposition-vs-polish §0):任何 perf attack 连续 2 轮 polish 没动针 → 立刻停。下一行不允许是"再 polish"或"declare ceiling",必须是"decomposition"。 — global methodology file imported into ~/.claude-shared/CLAUDE.md
Figure 4 — Phase A→B dance(完整 state machine)
Round 1-2 surgical polish 试有目标的优化;如果 2 轮内"动针"(累计 ≥ 1.5× variance band),继续 polish。 否则强制 Round 3 SWITCH —— STOP polish,Phase A read-only 拆完整 hot path,Phase B atomic 实施全 attack 清单,单次 cumulative bench 实测。 实测对照 Phase A 预测的翻盘表是这套 methodology 的核心价值产出 —— 翻盘项就是 polish 永远碰不到的位置。 若 gap 没关,Round 4+ 重新 decompose;不许 polish 同一 attack 清单。本会话 v1.5-v1.9 跑了 5 轮完整 dance + 1 个 refuted-by-measurement(A4)。

3. 已落地的几套完整模式

"模式"指 grpcx 在 transport / 调用方向 / 优化路径上提供的可独立组合的运行模式。本会话落地的模式如下:

Mode A:shmem busy-poll-unbounded v1.3 起 · 协议双端对称

两端 spin on ring head/tail,跳过所有 wake-fd syscall。每个 active 连接燃一核。

API:ShmemConnection::set_busy_poll_unbounded(true) + Server::listen_shmem_busy_poll_until(path, stop)。 适用 throughput / 低延迟敏感场景,burn-CPU 可接受时。lx64 shmem-throughput 34 GB/s 主要靠这个。

Mode B:shmem park-fallback v1.3 起 · v1.9 升级 Linux eventfd

busy-poll 一段时间后落到 wake-fd 阻塞。Linux 6.x 用 eventfd(2),Darwin/BSD 用 pipe(2)。

API:ShmemConnection::set_busy_poll_threshold(Duration)。 适用低 QPS 低 CPU 场景。lx64 park RTT 3.54 µs(at Linux kernel floor)。

Mode C:shmem zero-copy server-streaming v1.5 起 · 客户端 opt-in,additive API

Client 不通过 owned Vec<Vec<u8>> 收;直接通过回调拿到 &[u8] view 进 shmem 槽 → 用完 advance reader_pos → 槽可被覆盖。

API:ShmemConnection::call_server_streaming_view<F: FnMut(&[u8])>(...)。 lx64 上从 server-streaming 路径削掉 ~1100 ns/帧。

Mode D:tcp-mux v2 SQPOLL(Linux 默认) v1.1 起 · Linux + feature 自动启用

io_uring SQPOLL + linked send-pair + send buffer pool。SQ kernel thread 帮你 poll SQE,client 写 SQE 不用 syscall。

API:Server::listen_tcp_mux_v2_until + 启用 transport-tcp-mux-iouring feature。默认在 Linux + feature 自动用。

Mode E:tcp-mux v2 server-side busy-poll v1.4 起 · deployer opt-in

Server thread 不阻塞 SQ kernel thread,改 nonblocking socket + core::hint::spin_loop。绕过 SQPOLL kernel-thread overhead。

API:Server::listen_tcp_mux_v2_busy_poll_until。lx64 tcpmux-rtt 默认 8.30 µs → 6.60 µs,RFC < 8 µs gate 由这条 mode close。

Mode F:UDS standard blocking v1.0 始 · 唯一 mode

blocking read_exact + writev 单 socket per connection。无 busy-poll 等价(net.Socket 强制 libuv event-loop driven)。

API:UdsConnection::connect + Server::listen_uds_until。lx64 5.56 µs,at Linux 6.12 syscall floor。

Mode G:TS+N-API+shmem with busy-poll v1.7 起 · TS 端配合 server SHMEM_BUSY_POLL=1

TS ShmemConnection.setBusyPollUnbounded(true) 跳过 wakeWrite/wakeRead,Node 主线程 spin on ring head。

API:TS 侧 setBusyPollUnbounded;Rust 服务器 env SHMEM_BUSY_POLL=1 触发 listen_shmem_busy_poll_until。lx64 TS shmem-rtt 12.28 → 5.44 µs。

Mode H:bench harness CPU 亲和 v1.9 后 · bench infra,不影响产品代码

Bench 加 --pin-server N --pin-client M 走 Linux sched_setaffinity(2)。让 SMT-sibling 实测 + 排除 scheduler placement 干扰。

实测:SMT 邻居 pin(cores 0,8)对 lx64 shmem-rtt-busy 的 median 不动(2.3 µs),只 tighten p99(3.5 → 2.6 µs)。bimodality 不是 scheduling 而是 cache-coherency timing。

9. 未关 gate 的 earned ceiling 论证

实测 per-syscall 一致性验证 Linux 6.12 / i7-10700K kernel floor 在 ~0.9 µs:

  • shmem-rtt-busy min 515 ns = 用户态(无 syscall)真实 floor
  • shmem-rtt-park 3540 ns ÷ 4 syscalls = 890 ns/syscall
  • uds-rtt 5564 ns ÷ 6 syscalls = 930 ns/syscall

两个 gate 的 per-syscall 一致 → 都已 at Linux 6.12 + i7-10700K kernel floor。继续推进需要 runtime-tier change:

  • shmem-rtt-park < 3 µs 需要消 1 个 wake-fd syscall(conditional wake_signal + consumer_blocked atomic flag);但 single-in-flight RPC 形状下 saving = 0(consumer 总 blocked between RPCs);streaming 形状下有 saving 但 streaming 走 busy-poll 路径(v1.3 已)
  • uds-rtt Rust < 5 µs 需要消 1 个 read syscall(buffered FrameReader);v1.4 试过 + reverted by measurement(loopback kernel coalesce 已快 + Vec alloc 抵消)
  • TS+N-API+UDS < 15 µs 还差 ~1 µs;net.Socket._handle bypass refuted by measurement on Node v26;await-less 已被 V8 fast-async 优化
  • TS+N-API+shmem < 1 µs 是 runtime-tier-conditional — 需要 Bun/Deno FFI 旁路绑定(per-call < 10 ns + busy-spin doorbell)
